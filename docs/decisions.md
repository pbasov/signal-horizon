### SD-11 — No UI framework; imperative DOM and Three.js only
**Status: ACCEPTED.** No React, Vue, Svelte, or any reactive/reconciliation layer. The frame loop is `requestAnimationFrame → sim.tick() → orrery.update(state) → renderer.render()` — no diffing, no virtual DOM, no scheduling, no effect lifecycle. Three reasons: (1) The orrery renders to a WebGL canvas — a framework can't schedule or diff GPU draw calls; a React-Three-Fiber wrapper adds JS overhead before the same GL calls. (2) A real-time sim updates every frame — position, packets, freshness all change every tick. Reactive frameworks optimise for skipping unchanged subtrees, but there's nothing to skip; the reconciliation cost is pure overhead. (3) GC pressure: each framework render cycle allocates vdom nodes, memo objects, and effect cleanup closures. At 60fps (~16ms/frame) this competes with the sim and orrery for the frame budget. The adversarial review caught ~960 `Vector3`/frame in Three.js — a framework's allocation pattern would compound this. Panels use `element.textContent = newValue` in the frame loop. If panel complexity grows later, the answer is writing that component imperatively, not introducing a framework.

### SD-15 — Port the save/replay backbone + M1 economy from the tested C# reference
**Status: ACCEPTED.** Source PLAN/SPIKE. The save/replay backbone (P0-05/06) and the M1 economy are **not greenfield** — they are ported from the complete, tested C# reference at `/home/basov/Games/Godot/galaxy-link/SignalHorizon.Sim/` (`SaveGame`/`SimAction`/`StateHash`/`SimScheduler` + `M1/{Cache,Coherence,Demand,Resolver,M1Economy}` + `Tests/{SaveReplayTests,M1ModelTests}.cs`).

**Finding from B1 — the C# golden state-hash is NOT bit-portable to TS.** `StateHash` was ported byte-for-byte to `src/sim/state-hash.ts` (verified: identical fold constants `Mult=1000003`/`Seed=1469598103934665603`, little-endian IEEE-754 byte order, sort order, hashed quantities, unsigned-u64 fold). Yet `canonicalHash` over the golden ticks `{0,3600,86400,2592000}` at `dt=1/60` yields **12899997400407946598** in TS vs **15552073864691245897** (unsigned u64) in C#. Cause: of the 96 folded position doubles, two differ in their lowest 1–2 mantissa bits (`sat_meo_inc.z@t0`, `mars.y@t3600`) — V8-vs-.NET `Math.sin/atan2/sqrt` rounding, the same sub-ULP divergence `ephemeris.test.ts` already tolerates at `REL_TOL=1e-9`. A raw-bit hash has full avalanche, so 1 ULP scrambles the result; matching C# would need an fdlibm-identical trig port (out of scope). **Resolution:** pin the TS-native value as the determinism guard, record the C# baseline as provenance. P0-06 is therefore an *intra-runtime* TS determinism proof (replay → identical TS state), not a cross-runtime C# equivalence proof; the **replay golden (B3) should fold the action-driven mutable state** (clock tick, RNG state, economy integers — all exactly representable), not the transcendental ephemeris positions. The TS pin is stable for a fixed V8/Node (D1 pins Node 26).

Two C# porting traps still hold for SaveGame/replay: (1) `dt = 1/60` is stored as exact IEEE-754 bits and **does not survive JSON** — preserve the bit pattern, do not round-trip through a decimal string; (2) replay must use the **unclamped scheduler kernel** (`SimScheduler`), because the live `SimClock` drops steps under fast-forward and would diverge.

### SD-34 — M2-fix: anchor the M2 schedulers to the session start + clamp shock compounding (the live epoch-mismatch bug)
**Status: ACCEPTED (autonomous bugfix; live-only, no design change).** The live `BuildSession` is driven in `main.ts` on the SHARED clock, which boots at the M1 scenario epoch (`SCENARIO.tick0` ≈ 14.5M s — the conjunction approach). But the M2 schedulers were written assuming a session starts near t=0: the event generator (`FIRST_EVENT_AT_SECONDS = 2400`), the contract offer generator (first offer ~1800 s), and the demand-growth cadence (`lastGrowthAtS = 0`) all init their cursors near 0. On the FIRST live step at t ≈ 14.5M s every cursor was ~14.5M s OVERDUE, so the catch-up loops fired their whole backlog at once (the event generator hit its 64-fire cap), the per-cell demand-shock overlays compounded MULTIPLICATIVELY on shared cells (`shockMulScratch[id] *= m`), and the demand total ran to ~1e40 — the orrery DEMAND·GROWTH readout painted "+6.5e39%". The `m2-build-replay` golden drives from t=0, so it is internally consistent and never saw this: the bug was purely the live epoch mismatch.

**Fix 1 — lazy first-step schedule anchor (`session.ts` + the two generators).** On the FIRST `BuildSession.step(t)` (a one-time `anchored` latch), `anchorSchedulers(startT)` re-anchors every cursor RELATIVE to `startT`: `ContractGenerator.anchorAt`/`EventGenerator.anchorAt` set `nextOfferAtS = startT + FIRST_OFFER_AT_SECONDS` / `nextEventAtS = startT + FIRST_EVENT_AT_SECONDS`, and the demand-growth cursors become `lastGrowthAtS = startT`, `nextGrowthAtS = startT + GROWTH_INTEGRATION_SECONDS`. So a 14.5M-s boot schedules its first event at 14.5M + 2400, not a 14.5M-s backlog. **When `startT === 0` (the golden replay path) the re-anchor reproduces the EXACT constructor values, so the t=0 fold is byte-identical** — the lazy first-step anchor was chosen over a constructor arg precisely so the test (which steps from t=0) stays unchanged. `restore()` sets `anchored = true` so a resumed session keeps its snapshot cursors (never re-anchors).

**Fix 2 — clamp shock compounding (`session.ts applyShockOverlay`).** Each active shock contributes a per-cell multiplier ≥ 1.0 and overlapping shocks compound their PRODUCT; the compounded per-cell `shockMulScratch[i]` is now clamped at `MAX_SHOCK_MULTIPLIER = 4.0` (comfortably above a single shock's 2.6 peak, so normal overlaps are unclamped). Belt-and-suspenders next to the anchor: even a pathological concurrent-shock pile-up can never blow demand to Infinity.

**Fix 3 — guard the readout (`orrery.ts`).** The DEMAND·GROWTH segment now renders only when `baselineDemand > DEMAND_GROWTH_EPSILON (1e-9)` AND the growth % is finite + in `[0, DEMAND_GROWTH_MAX_PCT (1000)]`; otherwise the segment is OMITTED — the chrome can never paint scientific notation again (the sim, not the readout, would be wrong).

**Determinism.** The M2 build-loop golden stayed **`8431658617016421069n`** (the t=0 path is byte-identical) and the **M1 golden `544847093270497462n` is UNTOUCHED**. New `m2-epoch-anchor.test.ts`: starting a session at the 14.5M-s epoch fires **0** events on the first step (pre-fix: 64) with demand ratio **1.0** (pre-fix: ~877× on step 1, ~1e38 over time); demand stays bounded under sustained stepping at the live epoch; the clamp alone bounds a long shock-heavy run; LIVE==REPLAY holds at the large epoch; and the t=0 first-event still lands at ≥2400 s. 441→446 tests; tsc + build clean; `src/sim` pure (randomness only via the seeded PRNG). **Readout shown sane via** the CONTRACTS preset (key **7**) with the heatmap toggled (**H**) at the live epoch.

### SD-33 — M3a: the first orbital datacenter + the thermal/power model (compute as a force-multiplier)
**Status: ACCEPTED (autonomous decision; M3a, the first M3 spine ticket).** GDD §4.5 makes compute BUILDABLE INFRASTRUCTURE that force-multiplies the information loop — under the explicit hard constraint (Risk-5 / the Per Aspera cautionary tale): **a small number of high-impact strategic nodes you place/power/cool, NOT a sprawling base-builder.** M3a is the first such node + the §4.5 physics.

**The pure DC node + the two physical ceilings (`src/sim/m3/datacenter.ts`, pure).** A `Datacenter{ bodyId, subLatRad/subLonRad (its footprint anchor), panelM2, radiatorM2, rtg }`. `resolveDCCompute(eph, dc, t)` is the model: **POWER** = solarFlux(∝ 1/d² from the Sun, via `bodyDistanceAU`) × panelM2 × `PANEL_W_PER_M2_AT_1AU` (+ a constant `RTG_POWER_W` floor if fitted — distance-independent, the nuclear lever for the dark outer system); **COOLING** = radiative-only, a hard thermal rejection cap = radiatorM2 × `RADIATOR_W_PER_M2`; **COMPUTE BUDGET** = `min(power/COMPUTE_W_PER_UNIT, rejectableHeat/THERMAL_W_PER_UNIT)` — BOTH ceilings bite. Worked numbers (default 1.5 m²/1.5 m² node): Earth (1 AU) → 450 W, 8.33 u, THERMAL-limited; Mars (1.52 AU, solar-only) → 195 W, 3.90 u, POWER-limited (the 1/d² penalty); Mars + RTG → 1395 W, back to 8.33 u (the RTG rescues it). All dials are named constants.

**The force-multiplier (the §4.5 point — feeds the loop or it's cut).** `computeLiftMultiplier(compute) = 1 + MAX_COMPUTE_LIFT·c/(c+HALF)` — a saturating, capped (≤ +40%) lift. `DCRoster.liftFor(eph, region, t)` returns the BEST (max, not sum → no stacking runaway) lift of any DC whose SUB-POINT footprint (`DC_FOOTPRINT_RADIUS_RAD` great-circle cap, same body) covers the region centroid. `BuildSession.step()` reads it: an ACTIVE contract being SERVED earns `tariff × frac × lift × dt` (the lift applies only to served revenue — a breach penalty is untouched; "transmit conclusions not bytes").
